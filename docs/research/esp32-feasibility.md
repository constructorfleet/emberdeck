# ESP32 worker feasibility

**Decision: conditionally feasible as a worker that forwards EmberDeck's existing GRBL byte protocol to an already qualified controller.** A standalone ESP-IDF implementation is the best fit. Do not claim support for direct laser/motion control or ESPHome integration today. First change or prototype a bounded, resumable download contract: the current whole-job JSON response is not a safe assumption for MCU RAM. No board, electrical interface, or physical machine is qualified by this investigation.

This is a feasibility investigation for [issue #3](https://github.com/constructorfleet/emberdeck/issues/3), not an implementation. Its current acceptance criteria ask for a decision, architecture, board/controller limitations, hardware validation plan, and—if viable—prototype milestones. No issue comments were present when checked on 2026-10-27. The active server and worker behavior below was checked against `docs/api.md`, `docs/architecture.md`, `docs/serial.md`, `docs/worker.md`, `internal/server/lifecycle.go`, `internal/server/server.go`, `worker/worker.go`, and `driver/driver.go`.

## Existing EmberDeck boundary

EmberDeck has a server-owned persistent job library and authenticated HTTP worker poll protocol. A worker registers a process-unique session; an assignment grants one job and lease. It reports acknowledged executable lines and the last controller state, and terminal receipts are lease-bound. The server expires a worker after ten seconds without heartbeat. The Go worker polls each second, reports each second, and receives the complete `job.gcode` in its assignment JSON. The upload endpoint accepts up to 4 MiB of JSON. These limits and semantics are described in the [API contract](../api.md) and implemented in [`worker/worker.go`](../../worker/worker.go), [`server.go`](../../internal/server/server.go), and [`lifecycle.go`](../../internal/server/lifecycle.go).

The controller implementation validates the full program, sends one line at a time, and waits for GRBL acknowledgment. It checks fresh initial status, reports acknowledged-line progress, injects and acknowledges `M5`, and completes only after `Idle`. Pause needs fresh `Hold:0`/`Idle`; resume needs fresh `Run`/`Idle`; one connection and lease stay active while paused. Poll failure cancels the stream. Cancellation attempts a bounded hold/reset but is not a physical stop. Heartbeat expiry/server restart interrupts active work. A device must never reconnect and replay a job or infer resume from reboot/status alone. See the [driver contract](../driver.md), [worker contract](../worker.md), and [architecture](../architecture.md).

## Architecture comparison

| Approach | Fit | Decision |
| --- | --- | --- |
| Standalone ESP-IDF worker firmware | Can own Wi-Fi, TLS, session/lease polling, bounded job transfer, GRBL UART, watchdog/failure states, and diagnostics without changing EmberDeck's controller boundary. | **Preferred conditional prototype.** Implement a small state machine, not a general GRBL controller. |
| ESPHome external component | External components compile into ESPHome builds; its native API/OTA target Home Assistant, not EmberDeck sessions, leases, acknowledgments, or pause rules. It does not solve full-job RAM or prove safe behavior. ESPHome excludes custom components from security support. | **Not the runtime.** Could only be an optional configuration wrapper around the same tested worker core. [External components](https://esphome.io/components/external_components/), [security scope](https://esphome.io/guides/security_best_practices/). |
| Existing motion firmware (FluidNC) | FluidNC is active ESP32 CNC firmware with GRBL-compatible G-code, machine configuration, and its own web UI. It directly owns motion/laser outputs rather than acting as a network-to-existing-controller bridge. | Use only as a **controller endpoint** after separate compatibility and hardware qualification; do not embed it as EmberDeck worker firmware. It duplicates the existing GRBL controller role and changes the safety/qualification scope. [FluidNC project](https://github.com/bdring/FluidNC). |
| Existing serial bridge (ESP-Link) | ESP-Link describes an ESP8266 Wi-Fi/serial bridge on TCP port 23. Multiple clients can intermix serial input; its README calls master unstable and lists v2.2.3 as latest. | **Reject as worker.** It lacks EmberDeck leases/control/progress/no-replay. A bridge is only a transport fixture with exclusive access and separate worker software. [ESP-Link README](https://github.com/jeelabs/esp-link). |

Keep the present boundary: EmberDeck owns jobs and authorization; a single-purpose MCU worker owns one active lease and translates protocol bytes; a separate GRBL-compatible controller owns motion and laser outputs. The candidate MCU must not drive stepper/laser outputs in this scope. This avoids treating network connectivity as a safety function and avoids claiming a new direct-control firmware before its entire motion-control stack is qualified.

## Payload and device resources

The accepted job size is 4 MiB **including JSON overhead**, and assignment returns the full G-code string in one JSON response. The Go worker reads up to 8 MiB before decoding; an MCU can need response, decoded program, and parser storage at once. ESP32-S3 has 512 KiB internal SRAM, insufficient for that naive approach. Espressif lists modules with up to 16 MiB PSRAM and DevKitC-1 N8R8 with 8 MiB octal PSRAM; this makes a streamed/PSRAM prototype plausible but does not prove available headroom under TLS. [ESP32-S3 specifications](https://www.espressif.com/en/products/socs/esp32-s3), [WROOM-2 datasheet](https://documentation.espressif.com/esp32-s3-wroom-2_datasheet_en.html), [DevKitC-1 user guide](https://documentation.espressif.com/api/resource/path/docs/projects/esp-dev-kits/en/latest/esp32s3/esp32-s3-devkitc-1/user_guide_v1.1.html).

Prototype against **bounded chunks or a streaming response**, with the server preserving a single lease and the device validating before the first controller byte. Prefer a two-phase job fetch with immutable content digest/size, chunk range or chunk sequence, and a final verify step; keep server-side whole-program validation authoritative. A temporary-file approach requires adequate flash/partition design and wear analysis. External PSRAM can be used as a bounded buffer, not as evidence that the present protocol is safe. A limited first prototype may impose a lower job-size cap, but that cap must be enforced by server and device and documented. Do not silently truncate or start a partial job.

## Network, credentials, discovery, and update model

For a remote server, the worker needs Wi-Fi, HTTPS server verification, DNS/time handling, certificate roots or a managed pin-rotation plan, and a device-unique credential. EmberDeck currently shares one API key between operators and workers and has no RBAC; putting the global bearer secret on a device expands its exposure. Require a revocable worker credential bound to identity/capabilities before production. Do not accept plaintext HTTP on untrusted networks. ESP-IDF offers HTTPS OTA and certificate-bundle verification, but not EmberDeck's update policy. [ESP-IDF HTTPS OTA and root verification](https://docs.espressif.com/projects/esp-idf/en/latest/esp32/api-reference/system/esp_https_ota.html), [ESP-IDF secure boot guidance](https://docs.espressif.com/projects/esp-idf/en/latest/esp32/security/secure-boot.html).

Provision Wi-Fi/server URL over USB/serial or a physically initiated setup mode. Discovery must be opt-in, status-only, and never expose keys or assign work. Local diagnostics should redact credentials and report controller state, lease digest, progress, firmware version, and fault. Persist pin/baud/server changes atomically after deliberate provisioning.

Firmware updates need authenticated, integrity-checked images, rollback/recovery, and power-loss testing. ESP-IDF supports OTA rollback and secure transport; review fuse programming and recovery implications before enabling Secure Boot or flash encryption on production units. [ESP-IDF OTA security](https://docs.espressif.com/projects/esp-idf/en/v5.3.4/esp32/security/security.html), [Secure Boot](https://docs.espressif.com/projects/esp-idf/en/latest/esp32/security/secure-boot.html). Current ESPHome OTA docs describe optional pre-shared-key encryption (documented for ESPHome 2026.9.0+) and safe mode; this depends on configured firmware and does not replace EmberDeck device identity or release policy. [ESPHome OTA](https://esphome.io/components/ota/esphome/).

## Controller connection and candidate board

Candidate for bench prototyping only: **Espressif ESP32-S3-DevKitC-1-N8R8**, listed with 8 MiB flash and 8 MiB octal PSRAM at 3.3 V SPI. It is not a supported production board. Connect UART TX/RX/GND only to a verified compatible GRBL 1.1 controller port. ESP32-S3 has three configurable UARTs, but usable pins, boot/strapping pins, console conflict, USB connector behavior, and GPIO availability depend on exact board revision/module. [DevKitC-1 user guide](https://documentation.espressif.com/api/resource/path/docs/projects/esp-dev-kits/en/latest/esp32s3/esp32-s3-devkitc-1/user_guide_v1.1.html), [ESP-IDF UART](https://docs.espressif.com/projects/esp-idf/en/latest/esp32s3/api-reference/peripherals/uart.html).

ESP32 GPIO is a 3.3 V domain; no board spec establishes the target controller's UART voltage, isolation, or compatibility. Before wiring, verify idle voltage, logic thresholds, grounding/isolation, pinout, baud/framing, reset-on-open, and sender contention. Use appropriate level shifting/isolation; never connect GPIO directly to 5 V or RS-232, stepper-driver signals, or laser enable/PWM. Distinguish three paths: the chosen controller link is UART TX/RX; the S3's native USB Serial/JTAG CDC works directly to a PC for console/flashing without a USB-UART bridge; hosting a USB CDC controller as USB host is a separate, unqualified design and is not implied by native USB Serial/JTAG. [S3 electrical specs](https://documentation.espressif.com/esp32-s3-wroom-2_datasheet_en.html), [native USB Serial/JTAG](https://docs.espressif.com/projects/esp-idf/en/release-v5.5/esp32s3/api-guides/usb-serial-jtag-console.html), [UART-to-PC connection options](https://docs.espressif.com/projects/esp-idf/en/latest/esp32s3/get-started/establish-serial-connection.html).

No common board is supported yet. The N8R8 is a practical resource-rich prototype candidate; a no-PSRAM ESP32-S3 or another ESP32 variant should not be accepted until the selected streaming/buffer design passes RAM and TLS stress tests. Board-specific safety outputs, interlocks, and emergency-stop circuits remain external and independent of firmware.

## Required worker state and failure behavior

Implement and test this contract before connecting a laser-capable machine:

- One process/device boot creates a fresh session. One assignment lease is executed once; lost poll/receipt responses must not cause source replay. A reset loses active execution state and reports/re-registers so the server marks the old lease interrupted. Never auto-resume on boot, reconnect, or a controller `Run`/`Idle` observation.
- Validate job size, framing, digest, and all G-code before sending the first byte. Then send one line and wait for exactly one expected acknowledgment; report `acked`, `total`, and controller status. Complete only with all source lines acknowledged, injected/acknowledged `M5`, then `Idle` confirmed by a fresh query.
- Keep the same lease and controller connection through pause. A pause assignment before source output must gate all output. Pause uses GRBL feed hold, reports `pausing` through `Hold:1`, and only reports `paused` after fresh `Hold:0`/`Idle`. Resume requires the server's explicit resume command and a fresh post-command `Run`/`Idle`; never infer permission from status alone.
- Cancel, watchdog expiry, brownout/reset, UART error, HTTP/TLS failure, heartbeat expiry, invalid response, or controller timeout must gate further G-code immediately and take a bounded best-effort hold/reset where the controller protocol supports it. The server must be allowed to interrupt the lease. No software path can promise that the physical laser is off; independent interlocks and emergency stop stay in series with laser enable.
- Power interruption during firmware update must boot either the old known-good image or a recovery mode, never an unsafe partially updated image. A failed update must not reset or requeue a job. Firmware health checks must occur with laser output disabled.

GRBL status/ack behavior and controller capabilities must be verified against the exact controller firmware, since current EmberDeck documents GRBL 1.1 compatibility but has no physical controller qualification. See the [GRBL interface](https://github.com/gnea/grbl/blob/master/doc/markdown/interface.md) and [realtime commands](https://github.com/gnea/grbl/blob/master/doc/markdown/commands.md).

## Prototype gates and hardware qualification

1. **Contract prototype (no motion hardware):** Specify chunked/digest-checked job transfer and worker credential scope; add a fake HTTP server and fake UART target. Demonstrate fresh session, single lease, progress monotonicity, duplicate/lost receipts, malformed/truncated job rejection, and no output before complete verification.
2. **Protocol prototype (controller with motor/laser outputs disconnected):** Implement ESP-IDF worker state machine on N8R8. Run UART transcripts for initial `Idle`, each `ok`, errors, alarm, stale status, hold `Hold:1`/`Hold:0`, pause-before-first-line, resume fresh status, cancel, and timeout. Assert exact emitted bytes and no G-code after each injected failure. Exercise heap/PSRAM high-water use under TLS, maximum configured job, Wi-Fi reconnect, bad clock/certificate, server outage, and watchdog reset.
3. **Electrical bench qualification:** For each named board and controller combination, document schematic/connector, voltage levels, isolation, ground/reference, baud/reset behavior, EMC/noise, power brownout, boot pin states, and USB/UART contention. Verify boot/reset/update failure always leaves laser enable de-energized at hardware level.
4. **Machine qualification (separate approval/evidence):** Keep laser disabled initially; use a test controller load, then motion-only with laser physically disconnected, then manufacturer-approved low-power test in an enclosed machine. Measure stop/hold latency and failure response under Wi-Fi loss, server loss, MCU reset, and controller disconnect. Verify independent door interlock, emergency stop, extraction, fire safeguards, and restart procedure. Publish supported board/controller/firmware/baud matrix only after signed test reports and operator instructions exist.

**Acceptance scope:** Conditional feasibility and prototype design only. ESP32-S3-DevKitC-1-N8R8 is a candidate, not a supported board. ESPHome is unsuitable as the job-worker runtime unless it can host the exact lease/control contract without compromising failure behavior; current docs give no such integration. FluidNC is a direct motion controller option, not a bridge implementation. Blockers before a viable user-facing feature: bounded payload protocol, separate worker identity, secure update lifecycle, exact UART electrical target, and successful physical qualification. No firmware, board, or laser operation is claimed available.
